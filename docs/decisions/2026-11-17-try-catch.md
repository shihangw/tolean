# Start with catches that do not need a changed environment

We will add `try { … } catch (e) { … }` first for try bodies that do not
change outer variables. The handler resumes with the environment from entry
to the try body. This restriction is part of acceptance, not an assumption
that a certificate asks its caller to prove.

The current statement evaluator keeps an environment on normal completion,
break and continue. A return or throw keeps only an `Except` value. It cannot
recover a variable's value after a try body assigns that variable and then
throws. Passing the entry environment to a handler would give the wrong
answer in that case. The translator must therefore refuse outer assignments
and calls that change captured state inside a try body.

A caught error must be a modeled thrown value. Some built-in operations
currently give no evaluator result where JavaScript throws. Those operations
must remain refused inside a try body. No evaluator result must not become
an exception that a handler can catch.

The syntax tree will retain both blocks and the catch binding. The parser
and printer will preserve the statement through their existing round-trip
theorems. The evaluator will distinguish a thrown completion from a returned
completion before selecting a handler. Translation must establish that the
generated handler makes the same selection under `program_sound`.

The first version will refuse `finally`, mutable try bodies and unsupported
rethrows from a handler. `finally` needs rules for overriding an earlier
completion. Mutable try bodies need environments on thrown completions and
a stronger statement simulation theorem. Rethrows need a typed representation
of the caught value that the translator can pass back unchanged. These are
separate extensions, not reasons to interpret any of these forms as a
no-op.

This decision settles the plan's initial scope. It does not mark step 17
complete. The TypeScript guide and acceptance tests will describe only the
forms that the implementation actually accepts.
